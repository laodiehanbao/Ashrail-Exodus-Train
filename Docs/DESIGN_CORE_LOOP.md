# DESIGN_CORE_LOOP

本文档定义《烬轨：流亡列车 / Ashrail Exodus Train》第一阶段可交付闭环。目标是先做出可验证、可调参、可继续扩展的原型闭环，而不是一次性演示。

## 第一阶段目标

第一阶段只覆盖原型核心：

- 列车展示：能看到车头与基础车厢状态。
- 自动战斗：进入关卡后自动遭遇敌人并结算胜负。
- 掉落与奖励：战斗、事件或宝箱产出资源、装备、模块碎片。
- Loot Box：通过配置表开箱，展示奖励结果。
- 成长反馈：资源、装备、列车模块让战力上涨。
- Mock 广告：广告只通过接口模拟，不接入真实平台 API。
- Local Save：本地存档有版本号，可保存关键进度。

## 第一轮闭环

第一轮必须能从空存档跑通以下路径：

```text
启动游戏
  ↓
加载本地配置与默认存档
  ↓
进入第一关巡航
  ↓
自动生成敌人并结算战斗
  ↓
获得资源 / 装备 / 模块碎片
  ↓
打开补给箱或领取关卡奖励
  ↓
升级装备或列车模块
  ↓
战力提升并解锁下一阶段压力点
  ↓
可选择 Mock 广告翻倍奖励
  ↓
写入本地存档并返回巡航
```

## 关键体验点

- 奖励反馈必须明确：奖励列表、稀有度、战力变化、资源变化。
- 战斗不追求复杂操作，优先保证自动结算稳定、节奏短、反馈强。
- 开箱是第一阶段最重要的满足点，必须支持稀有度颜色和结果展示。
- 广告入口必须自然：奖励翻倍、离线收益、失败续航，不强行打断主循环。
- 列车成长需要可见：模块等级、插槽状态、战力来源至少能被 UI 表达。

## 数据驱动边界

第一阶段不得硬编码以下内容：

- 敌人生命、攻击、奖励。
- 关卡波次、目标、解锁条件。
- 装备名称、稀有度、基础属性。
- 宝箱奖池、概率、保底策略。
- 广告奖励倍率、冷却、每日次数。
- 模块升级费用、属性增量。

这些内容必须来自 `configs/` 或 `src/data` 的配置入口，并通过 schema 或校验函数验证。

## 系统边界

- UI 只发送请求和展示结果，不计算掉落、不改存档。
- 战斗结果由 `gameplay` 的战斗系统计算。
- 奖励发放由奖励服务统一处理。
- 背包、资源、列车模块属于 `domain` 数据模型。
- 广告通过 `IAdService`，第一阶段使用 `MockAdService`。
- 存档通过 `ISaveService`，第一阶段使用 `LocalSaveService`。

## 第一阶段验收

完成第一轮闭环时必须满足：

- 新存档能完成至少 3 个连续关卡或巡航阶段。
- 固定随机种子下，开箱结果可复现。
- 战斗模拟可在测试或脚本中独立运行。
- 奖励结算幂等：同一结算 ID 不重复发奖。
- 存档包含版本号，能处理缺字段默认值。
- 广告失败、取消、无填充均不会阻塞主循环。
- UI 未直接调用平台 API、未直接写入核心存档。
